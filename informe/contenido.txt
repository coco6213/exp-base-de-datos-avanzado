@@H RESUMEN
Distribuidora Andina Comercial S.A.C. (empresa ficticia del caso DataShield 360) vende productos de consumo masivo en Lima, Arequipa y Trujillo, pero decide con reportes de Excel hechos a mano a fin de mes y su base de datos SQL Server no tiene automatización, auditoría ni respaldos formales. Este avance (semana 6) cubre el proyecto hasta el tema de Inteligencia de Negocios y Visualización de Datos. El objetivo fue construir una solución BI segura y medible: una base transaccional de 11 tablas con 3 procedimientos almacenados, 2 triggers de auditoría, 3 roles y política de respaldo; un proceso ETL con 5 reglas de limpieza; un Data Warehouse en esquema estrella con índice columnar; y un dashboard en Excel con 4 KPI, 4 gráficos y filtros OLAP. Se usó un dataset simulado y reproducible de 200 000 ventas y 599 806 líneas de detalle (2023-2025). Para validar la solución se diseñó un experimento con 3 escenarios (base transaccional sin índices, con índices y Data Warehouse) y 4 consultas de negocio, midiendo tiempo, CPU y páginas leídas con 10 repeticiones. El Data Warehouse respondió los reportes entre 7,7 y 11,5 veces más rápido y leyó entre 87 % y 95 % menos páginas; los índices tradicionales solo aceleraron la búsqueda puntual de un cliente. El ETL cuadró al céntimo con el origen (S/ 180 113 494,64) y las 8 pruebas funcionales y de seguridad pasaron. Se concluye que separar la base del día a día del Data Warehouse es la decisión técnica correcta para el análisis gerencial. La solución Big Data (PySpark) y NoSQL (MongoDB) se desarrollará en la entrega final.
Palabras clave: data warehouse, esquema estrella, ETL, índice columnar, OLAP.
@@H ABSTRACT
Distribuidora Andina Comercial S.A.C. (a fictitious company from the DataShield 360 case) sells consumer goods in Lima, Arequipa and Trujillo, but it makes decisions with hand-made Excel reports at the end of each month, and its SQL Server database has no automation, auditing or formal backups. This progress report (week 6) covers the project up to the Business Intelligence and Data Visualization topic. The goal was to build a secure and measurable BI solution: an 11-table transactional database with 3 stored procedures, 2 audit triggers, 3 roles and a backup policy; an ETL process with 5 cleaning rules; a star-schema Data Warehouse with a columnstore index; and an Excel dashboard with 4 KPIs, 4 charts and OLAP filters. A simulated, reproducible dataset of 200,000 sales and 599,806 detail lines (2023-2025) was used. To validate the solution, an experiment with 3 scenarios (transactional database without indexes, with indexes, and Data Warehouse) and 4 business queries was designed, measuring time, CPU and pages read over 10 repetitions. The Data Warehouse answered the reports between 7.7 and 11.5 times faster and read between 87% and 95% fewer pages; traditional indexes only sped up the single-customer lookup. The ETL reconciled to the cent with the source (S/ 180,113,494.64) and all 8 functional and security tests passed. We conclude that separating the day-to-day database from the Data Warehouse is the right technical decision for management analysis. The Big Data (PySpark) and NoSQL (MongoDB) solution will be developed for the final delivery.
Keywords: data warehouse, star schema, ETL, columnstore index, OLAP.
@@H 1.1 Contexto y necesidad empresarial
Distribuidora Andina Comercial S.A.C. es una empresa ficticia que distribuye productos de consumo masivo (abarrotes, bebidas, lácteos, limpieza, snacks, etc.) a bodegas, minimarkets y mayoristas desde 6 almacenes en Lima, Arequipa y Trujillo. Sus procesos críticos son: ventas, control de inventario y distribución.
Usuarios: vendedores (registran ventas), jefes de almacén (controlan stock), gerencia comercial y general (deciden metas, compras y campañas) y el área de TI liderada por Diego Paredes.
Situación actual (línea base del caso): la base SQL Server no tiene procedimientos estandarizados ni triggers de auditoría, los respaldos son manuales y los gerentes deciden con reportes de Excel que se arman una vez al mes. Además, la autoridad de protección de datos exige demostrar cumplimiento en 60 días. El caso cita que el 78 % de empresas peruanas medianas tuvo incidentes de pérdida de datos y que el 91 % decide sin soporte analítico formal.
Línea base cuantitativa usada en este proyecto: 200 000 ventas en 3 años (≈ 5 556 por mes), 599 806 líneas de detalle y S/ 185,6 millones facturados (incluye anuladas). Antes de la solución, un reporte por región y mes debía construirse a mano; con la base actual sin optimizar la consulta equivalente tarda en promedio 266 ms y lee 4 818 páginas (escenario E1 del experimento).
@@H 1.2 Formulación del problema de ingeniería
Problema: ¿cómo transformar una base de datos transaccional sin controles en un ecosistema de datos que proteja la información y entregue indicadores de ventas confiables y rápidos para la gerencia, sobre cientos de miles de registros que crecen cada año?
Causas: (1) la misma base sirve para registrar ventas y para hacer reportes, lo que la vuelve lenta para analizar; (2) no hay reglas automáticas que eviten errores (por ejemplo, vender sin stock); (3) no se registra quién cambia datos sensibles; (4) los datos tienen problemas de calidad (ventas anuladas mezcladas, nombres con espacios, emails vacíos).
Consecuencias: decisiones tardías (un mes de retraso), riesgo de sanción por la Ley N.° 29733, pérdida de información ante fallas y reportes que no cuadran.
Restricciones: usar SQL Server (motor de la empresa), equipo de laboratorio de un solo servidor, costo cero en licencias (edición Developer y herramientas Office ya disponibles), datos ficticios y plazo de 6 semanas para este avance.
Por qué BI y Big Data: la solución BI (Data Warehouse + ETL + dashboard) resuelve la necesidad de indicadores confiables; la solución Big Data (PySpark, entrega final) atenderá el crecimiento del volumen (más de 40 % anual según el caso) y datos no estructurados que una sola base relacional no procesa con eficiencia.
@@H 1.3 Objetivos
Objetivo general: implementar y validar una solución de Inteligencia de Negocios sobre SQL Server para Distribuidora Andina que entregue indicadores de ventas reconciliados al 100 % con el origen y responda los reportes gerenciales al menos 5 veces más rápido que la base transaccional, protegiendo los datos personales con roles y auditoría.
Objetivos específicos:
OE-01 (Base y automatización): crear la base transaccional con al menos 6 tablas relacionadas, 3 procedimientos almacenados y 2 triggers con TRY-CATCH y COMMIT/ROLLBACK, verificados con pruebas.
OE-02 (BI – ETL y Data Warehouse): diseñar un esquema estrella con 1 tabla de hechos y al menos 3 dimensiones y un ETL con al menos 3 reglas de limpieza cuya reconciliación tenga diferencia S/ 0,00.
OE-03 (BI – Visualización): construir un dashboard con al menos 4 visualizaciones, KPI de ventas, análisis OLAP por tiempo, región y producto y un gráfico de tendencia.
OE-04 (Experimentación): medir con al menos 3 escenarios y 10 repeticiones el tiempo y las lecturas de consultas analíticas para justificar el modelo elegido.
OE-05 (Big Data – entrega final): procesar con PySpark un dataset de al menos 10 000 registros y evaluar su escalabilidad.

@@H 2.1 Antecedentes
A1. Chaudhuri y Dayal (1997) revisaron la tecnología de data warehousing y OLAP. Problema: las bases operativas no sirven para análisis. Método: arquitectura con extracción, limpieza y carga a un almacén separado y modelado multidimensional (estrella y copo de nieve). Métricas: conceptuales. Aporte: justifica separar la base OLTP del Data Warehouse y usar operaciones OLAP (drill-down, slice and dice) en nuestro dashboard.
A2. Kimball y Ross (2013) propusieron el diseño dimensional en cuatro pasos: elegir el proceso de negocio, declarar el grano, identificar dimensiones e identificar hechos. Datos: casos de retail y distribución. Resultado: modelos simples y rápidos para el usuario de negocio. Aporte: seguimos estos pasos para FactVentas (grano = un producto en una venta).
A3. Inmon (2005) definió el data warehouse como una colección de datos orientada a temas, integrada, variable en el tiempo y no volátil, construida de forma normalizada. Aporte: sirvió como alternativa comparada en la sección 3.2; elegimos Kimball por ser más rápido de implementar para un solo proceso (ventas).
A4. Abadi, Madden y Hachem (2008) compararon bases orientadas a columnas y a filas con el Star Schema Benchmark. Métrica: tiempo de consulta. Resultado: el almacenamiento por columnas fue aproximadamente un orden de magnitud más rápido en consultas analíticas, y simular columnas en una base por filas no logra ese beneficio. Aporte: anticipa el resultado de nuestro escenario E3 (columnstore) frente a E2 (índices por filas).
A5. Larson et al. (2011) presentaron los índices columnstore de SQL Server. Método: almacenamiento por columnas comprimido y procesamiento por lotes dentro del motor relacional. Resultado: mejoras de rendimiento de un orden de magnitud o más en consultas típicas de data warehouse. Microsoft (2025) indica hasta 10 veces más velocidad y hasta 10 veces más compresión que el almacenamiento por filas. Aporte: respalda usar CLUSTERED COLUMNSTORE en FactVentas y nos da una meta medible (≥ 5 veces más rápido).
@@H 2.2 Fundamentos de Inteligencia de Negocios
Inteligencia de Negocios (BI): convertir datos en información útil para decidir. En simple: pasar de "miles de ventas sueltas" a "cuánto vendimos por región este mes".
Integración y ETL: ETL significa Extraer (copiar de la base del día a día), Transformar (limpiar y ordenar) y Cargar (guardar en el almacén de análisis). En ELT primero se carga y luego se transforma dentro del destino.
Modelado dimensional: organiza los datos en una tabla de hechos (lo que se mide: cantidad e importe) rodeada de dimensiones (cómo se filtra: cuándo, qué, quién y dónde). Si las dimensiones no se dividen en sub-tablas es un esquema estrella; si se dividen, es copo de nieve.
Data warehouse y data mart: el data warehouse junta los datos de toda la empresa para analizarlos; un data mart es una parte enfocada en un área (por ejemplo, solo ventas). DW_Andina funciona como data mart de ventas.
OLAP: forma de analizar datos "en cubo": rebanar (slice, por ejemplo solo 2025), cortar en dados (dice, solo Lima y 2025), profundizar (drill-down, de año a mes) y girar (pivot, cambiar filas por columnas).
Indicadores (KPI): números clave con fórmula, meta y frecuencia, por ejemplo ventas totales o crecimiento anual.
Visualización: gráficos que permiten ver tendencias y comparar rápidamente; cada gráfico debe responder una pregunta de negocio.
@@H 2.3 Fundamentos de Big Data
Avance preliminar (se completa en la entrega final). Big Data no se justifica solo por usar una herramienta, sino por características medibles del problema:
Volumen: hoy 600 000 líneas en 3 años; con el crecimiento de 40 % anual que cita el caso, en 5 años se superarían 2 millones de líneas por año, más los datos de rutas y comentarios.
Variedad: comentarios de clientes y registros de rutas de distribución en JSON (no estructurados), que se almacenarán en MongoDB.
Velocidad y escalabilidad: Spark reparte el trabajo en varios procesos (particiones) y puede crecer agregando nodos, algo que un solo servidor SQL no hace.
Veracidad: las mismas reglas de calidad del ETL se aplicarán al dataset de Spark.

@@H 3.4.3 Procesos ETL/ELT y calidad
El ETL es el procedimiento almacenado dbo.usp_ETL_CargarDW (script 06). Funciona dentro de una transacción: si algo falla, hace ROLLBACK y anota el error en la bitácora ETL_Log. Pasos: (1) extraer las líneas de venta del OLTP; (2) perfilar y aplicar 5 reglas de calidad; (3) cargar dimensiones y hechos; (4) reconciliar los totales.

Resultado: se extrajeron 599 808 líneas, se rechazaron 17 667 (líneas de ventas anuladas) y se cargaron 582 141 en 11 segundos. La reconciliación dio S/ 180 113 494,64 en ambos lados (diferencia S/ 0,00).

Automatización de procesos de base de datos (obligatorio). Se implementaron 3 procedimientos y 2 triggers (script 03):
• usp_RegistrarVenta: registra cabecera, detalle y descuenta stock en una sola transacción; si falta stock, deshace todo (ROLLBACK).
• usp_ActualizarInventario: repone o ajusta stock; valida que el producto exista en la sede.
• usp_GenerarAlertasStock: crea alertas cuando el stock baja del mínimo (sin repetir alertas el mismo día).
• trg_Auditoria_Cliente y trg_Auditoria_Producto: guardan en AuditoriaLog quién hizo el cambio, cuándo, y cómo estaba el dato antes y después (en JSON).

@@H 4.1 Pregunta experimental, objetivo e hipótesis
Pregunta: ¿cuánto se reduce el tiempo de respuesta y las páginas leídas de las consultas de negocio al pasar de la base transaccional actual (E1) a la misma base con índices (E2) y a un Data Warehouse con índice columnar (E3)?
Objetivo: comparar los 3 escenarios con las mismas 4 consultas y el mismo dataset, para justificar con datos la arquitectura BI (relacionado con OE-02 y OE-04).
Hipótesis H1: E3 responderá las consultas analíticas (Q1-Q3) al menos 5 veces más rápido que E1. Hipótesis H2: E2 mejorará sobre todo la consulta puntual (Q4) y poco las analíticas.

4. Ejecutar 07_experimento.sql: para cada escenario y consulta hace 1 corrida en frío (vacía la memoria con DBCC DROPCLEANBUFFERS) y 10 en caliente, sin otros usuarios conectados.
5. El procedimiento usp_Medir guarda automáticamente tiempo, CPU, lecturas, filas y checksum de cada corrida en LabExperimento.dbo.Resultado.
6. El mismo script calcula promedio, desviación estándar, mínimo, máximo y % de mejora; grafico_experimento.ps1 genera los gráficos.
7. Se comparan los resultados con las metas de la sección 4.3 y se registran desviaciones en 6.2 y 6.5.
@@H 4.7 Riesgos, validez y limitaciones del experimento
• Caché: los datos en memoria aceleran las consultas; se controla midiendo por separado la corrida en frío y 10 en caliente.
• Variabilidad del equipo: la PC tiene otros programas abiertos; se reporta desviación estándar y se repitió el experimento 3 veces (RUN-01 a RUN-03).
• Datos simulados: la distribución es uniforme entre productos; datos reales pueden tener más concentración. Los resultados se generalizan a volúmenes similares en un solo servidor.
• Paralelismo: SQL Server usa varios núcleos, por eso el CPU puede ser mayor que el tiempo; se reportan ambos.
• Equivalencia: se validó que los 3 escenarios devuelven exactamente el mismo resultado (checksum idéntico), así la comparación es justa.

@@H 6.5 Análisis e interpretación técnica
Contraste con la hipótesis H1: se cumple. E3 fue 10,5 veces (Q1), 11,5 veces (Q2) y 9,5 veces (Q3) más rápido que E1 en las consultas analíticas, por encima de la meta de 5 veces.
Contraste con la hipótesis H2: se cumple. Los índices de E2 hicieron la búsqueda de un cliente (Q4) 105 veces más rápida (de 50,9 a 0,5 ms), pero en las consultas analíticas el tiempo casi no cambió (Q2 y Q3 ≈ 1,0 vez; Q1 1,4 veces), aunque leyeron 37 % a 48 % menos páginas.
Por qué: las consultas analíticas suman casi toda la tabla; un índice por filas ayuda a encontrar pocas filas, no a sumar todas. El columnstore solo lee las columnas que se usan y comprimidas (6 MB frente a 35 MB), por eso lee 92 % a 95 % menos.
Patrón y anomalía (EXP-03): en frío, E3 fue más lento en Q1 (1 192 ms) y Q4 (1 566 ms) que E1 (455 y 147 ms) porque la primera vez debe cargar los segmentos columnares a memoria; desde la segunda corrida es el más rápido. En un dashboard que se usa todo el día este costo inicial ocurre una sola vez.
Variabilidad: en RUN-01 la consulta Q1 en E1 tuvo una corrida atípica de 16 306 ms (desviación 5 077 ms) por actividad del equipo; en RUN-03 la desviación bajó a 11 ms. En RUN-02, E2 salió hasta 26 % más lento que E1 en Q1-Q3, lo que confirma que los índices no son una mejora segura para reportes. La conclusión sobre E3 se mantuvo en las 3 corridas (7 a 11 veces).
Compromisos de ingeniería: el DW agrega un proceso ETL (11 s por carga) y los datos del dashboard se actualizan por lotes, no al instante; a cambio, los reportes son 10 veces más rápidos y no afectan las ventas. Los índices de E2 ocupan 2,3 veces más espacio (79,7 MB frente a 35,2 MB) y hacen más lentas las inserciones.
Límites de inferencia: el experimento muestra que el cambio de escenario causa la mejora en este equipo y dataset, porque solo se cambió una variable a la vez; no permite asegurar el mismo factor con otro hardware, con muchos usuarios a la vez o con datos 10 veces más grandes (eso se medirá con Spark).

@@H 7.2 Conclusiones técnicas
Conclusiones preliminares del avance:
C1. El Data Warehouse con índice columnar es la arquitectura adecuada para los reportes: redujo el tiempo de las consultas analíticas entre 89,5 % y 91,3 % (9,5 a 11,5 veces más rápido) y las páginas leídas entre 92 % y 95 % frente a la base actual (figuras 14 y 15).
C2. Agregar índices a la base transaccional no resuelve el problema de los reportes: solo mejoró la búsqueda puntual (Q4, 105 veces) y en Q2-Q3 la mejora fue ≈ 0 %, además de duplicar el espacio usado.
C3. El ETL con 5 reglas garantiza información confiable: excluyó 17 667 líneas anuladas y cuadró al céntimo con el origen (S/ 180 113 494,64; diferencia S/ 0,00).
C4. El dashboard revela un patrón accionable: la campaña de noviembre-diciembre vende 2,5 veces más por mes que el resto del año, y las ventas anuales están estancadas (−0,41 % en 2025), por lo que la gerencia debe planificar stock y nuevas acciones comerciales.
C5. La automatización y la seguridad funcionan: las 8 pruebas pasaron, incluyendo el ROLLBACK de una venta sin stock y el bloqueo del email al rol analista.
@@H 7.3 Recomendaciones
R1 (prioridad alta): conectar todos los reportes al DW y programar el ETL diario con SQL Server Agent a la 01:00; impacto: datos de un día de antigüedad en lugar de un mes.
R2 (prioridad alta): programar los respaldos (completo semanal, diferencial diario y log cada 15 minutos) con SQL Server Agent y probar una restauración completa cada mes; impacto: pérdida máxima de 15 minutos de datos.
R3 (prioridad media): pasar a carga incremental (solo ventas nuevas) cuando el volumen supere 2 millones de líneas, para que el ETL no crezca en tiempo.
R4 (prioridad media): migrar el dashboard a Power BI en la entrega final si el laboratorio lo permite, para publicar y compartir en línea con control de acceso.
